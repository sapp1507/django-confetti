# План исправления ошибок django-confetti

Дата фиксации: 2026-07-30.

Основание: анализ ветки `dev` на commit `b8108b9`. Архитектура и текущее
состояние проекта описаны в корневом файле `PROJECT_CONTEXT.md`.

## Цель

Устранить подтверждённые ошибки в моделях, Python API, REST API, кэшировании,
seed/sync-командах и snapshots, затем привести зависимости и документацию в
соответствие с фактическим поведением библиотеки.

Работу следует разбивать на небольшие логические изменения. Для каждой ошибки
сначала добавляется регрессионный тест, затем исправление. Функциональные
изменения не следует смешивать с массовым форматированием.

## Контракт обратной совместимости

Исправления должны оставаться совместимыми с публичным интерфейсом версии
`0.4.2`. До выпуска следующей версии сохраняются:

- импорты `confetti.api.get`, `set_value` и `is_enabled`;
- текущие сигнатуры публичных Python-функций и приоритет вычисления значения:
  user override → global value → definition default → аргумент `default`;
- имена моделей, полей и существующие значения enum типов и scope;
- ключи конфигурации `settings.CONFETTI`, включая dotted-path для
  `RESPONSE_METHOD`;
- имена URL и существующие пути REST API;
- имена management-команд и ранее работавшие варианты их аргументов;
- возможность применить новые миграции поверх БД версии `0.4.2` без потери
  валидных определений и значений;
- форматы REST-ответов и snapshot payload, кроме явно документированных
  исправлений ошибочного поведения.

Если исправляется опечатка в имени CLI-аргумента, корректная и старая формы
временно поддерживаются одновременно, а старая помечается для будущей
deprecation. Перед добавлением ограничений новая data migration должна
детерминированно обработать ранее допустимые дубликаты и не удалять
единственное актуальное значение.

Исправление подтверждённой ошибки может менять только ошибочное поведение,
которое противоречит README, модели данных или существующим тестам. Такое
изменение закрепляется регрессионным тестом и отмечается в changelog. Если
выяснится, что внешние пользователи могли разумно полагаться на поведение,
нужен переходный период или отдельная настройка совместимости.

## 1. Зафиксировать исходное состояние

Статус: выполнено 2026-07-30. Подробный результат сохранён в
`docs/2026-07-30-baseline.md`.

- Проверить `git status --short` и не изменять несвязанные пользовательские
  файлы.
- Запустить `pytest -q` и сохранить перечень падений.
- Запустить `python manage.py check`.
- Запустить `python manage.py makemigrations --check --dry-run`.
- Создать отдельную рабочую ветку перед внесением исправлений.

Исходный результат на дату плана: 22 теста проходят, один тест падает; Django
показывает два предупреждения `fields.E010`, незаписанных миграций нет.

## 2. Закрепить семантику bool-настроек

Статус: выполнено 2026-07-30 после пересмотра продуктового контракта. Для типа
`bool` поле `enabled` является основным переключателем, а не признаком
видимости или доступности настройки. `default` намеренно синхронизируется с
`enabled` для совместимости с общим механизмом чтения значений.

План:

- сохранить синхронизацию bool `default` с `enabled` при создании и при
  изменении переключателя;
- исправить устаревший тест, который ожидал сохранения конфликтующего
  `default=False` при `enabled=True`;
- явно использовать `enabled` как fallback-источник истины в `is_enabled()`
  для bool-настроек;
- сохранить приоритет пользовательского и глобального override при включённом
  `enabled`; `enabled=False` по-прежнему выключает настройку для всех;
- не менять поведение `is_enabled()` для остальных типов;
- документировать отличие `enabled` от `editable`.

Критерий готовности: тесты подтверждают синхронизацию `default`, переключение
через `enabled`, устойчивость `is_enabled()` к рассинхронизированным старым
данным и запрет override для `editable=False`. Миграция не требуется.

Результат проверки: все 24 теста проходят; целевой набор bool/Python API — 7
тестов. `makemigrations --check --dry-run` подтверждает отсутствие изменений
моделей.

## 3. Исправить seed/sync-команды

Статус: выполнено 2026-07-30 с сохранением совместимости CLI версии `0.4.2`.

План:

- в `seed_from_settings()` согласовать значение `definitions` с management
  commands;
- исправить аргумент `-update-defaults` на `--update-defaults`;
- проверить, что `--dry-run` откатывает изменения и не маскирует посторонние
  исключения;
- добавить тесты для обычного запуска, `--categories-only`,
  `--definitions-only`, `--update`, `--update-defaults` и `--dry-run`;
- проверить идемпотентность всех режимов, где она ожидается.

Критерий готовности: интерфейс команд совпадает с README, каждый режим меняет
только заявленную область.

Результат: исправлены `--categories-only` и `--definitions-only`; добавлен
корректный `--update-defaults`, а прежний `-update-defaults` сохранён как
legacy alias. Dry-run откатывает рассчитанные изменения и перехватывает только
собственный сигнал rollback. Семь целевых и все 29 тестов проходят; изменений
моделей нет.

## 4. Исправить REST API

Статус: выполнено 2026-07-30 с сохранением существующих URL, успешных
response payload и правил `editable=False`.

План:

- заменить `code=` на `status=` в ответах 401 и 403;
- обрабатывать в `get_object()` только ожидаемое
  `SettingDefinition.DoesNotExist`, не скрывая программные ошибки;
- явно определить контракт изменения `editable=False` для staff/superuser;
- валидировать неизвестный scope вместо неявного выбора user scope;
- добавить тесты для anonymous, user, staff и superuser;
- добавить тесты для global/user scope, неизвестного scope, `value=null`,
  отсутствующей и защищённой настройки.

Критерий готовности: все ветви авторизации возвращают корректный HTTP status и
не приводят к `TypeError`.

Результат: ответы используют `status=` вместо несовместимого `code=`,
неизвестный scope возвращает 400 до проверки авторизации, а `get_object()`
подавляет только ожидаемый `DoesNotExist`. Закреплены ответы 401/403 и текущая
матрица прав user/staff/superuser. Семантика `value=null` намеренно оставлена
пункту 7, чтобы реализовать её одинаково в Python API, REST и admin. Десять
целевых и все 33 теста проходят; изменений моделей нет.

## 5. Привести зависимости к заявленному контракту

Статус: выполнено 2026-07-30 без добавления обязательных runtime-зависимостей.

Предпочтительный контракт: основной Python API работает только с Django, REST
API устанавливается через extra `drf`, Swagger — через extra `docs`.

План:

- убрать `icecream` из runtime-кода библиотеки и demo settings;
- убрать отладочные вызовы из тестов;
- обеспечить безопасный импорт основного пакета без DRF;
- решить, должен ли импорт `confetti.urls` без DRF завершаться понятной ошибкой
  или предоставляться только при установленном extra;
- проверить соответствие `pyproject.toml` реальным импортам;
- протестировать чистую установку основного пакета, extra `drf` и extra `docs`.

Критерий готовности: пакет работает в чистом окружении, установленном только из
`pyproject.toml`, а optional-возможности имеют явные зависимости.

Результат: `icecream` удалён из runtime и demo-конфигурации; основной API и
fallback response импортируются без DRF; `confetti.urls` при отсутствии DRF
выдаёт инструкцию установить extra `drf`. Extra `docs` теперь явно включает
DRF. Добавлены проверки optional imports, сохранён no-op без drf-yasg. Все 35
тестов проходят. Из временной копии успешно собраны wheel и sdist; исправлены
`MANIFEST.in` и современные SPDX-метаданные лицензии, артефакты в рабочем
репозитории не создавались.

## 6. Исправить модели и ограничения БД

Статус: выполнено 2026-07-30 с совместимой data migration `0004`.

План:

- заменить изменяемые `default=[]` у `JSONField` на callable `default=list`;
- создать миграцию;
- гарантировать не более одного global value на definition;
- гарантировать не более одного user value на пару definition/user;
- запретить пользователя у global scope и потребовать его у user scope;
- использовать условные `UniqueConstraint` и `CheckConstraint`;
- перед ужесточением ограничений предусмотреть безопасную обработку уже
  существующих дубликатов.

Критерий готовности: `python manage.py check` не выдаёт `fields.E010`,
некорректные сочетания scope/user отклоняются БД.

Результат: JSON defaults используют callable `list`; добавлены отдельные
условные unique constraints для global и user values и check constraint для
согласованности scope/user. Перед ограничениями migration `0004` сохраняет
первую рабочую строку старого API, предпочитает валидную строку конфликтующей
невалидной и нормализует единственные legacy-значения. Реальный переход
`0003 → 0004` покрыт миграционным тестом. Все 41 тест проходят, Django system
check чистый, незаписанных миграций нет. Конструкция CheckConstraint совместима
с Django 3.2–5.x.

## 7. Уточнить и исправить валидацию значений

Статус: выполнено 2026-07-30 с реализацией reset через удаление override.

Сначала нужно закрепить контракт `None`. Предпочтительное поведение:
`value=null` удаляет соответствующий override и возвращает вычисление к
следующему уровню fallback, а не сохраняется как самостоятельное значение.

План:

- реализовать согласованную обработку `None` в Python API, serializer и admin;
- учитывать флаг `required`;
- для `datetime` определить и документировать допустимый ISO-формат;
- для `duration`, `int` и `float` возвращать приведённое значение;
- безопасно проверять структуру `choices`, не допуская `KeyError`;
- добавить параметризованные тесты для всех типов и ошибочных значений.

Критерий готовности: одинаковое значение одинаково обрабатывается Python API,
REST API и Django Admin.

Результат: `None` в Python/REST удаляет user/global override и возвращает
fallback; для required-настройки удаление запрещено, если fallback отсутствует.
Admin не позволяет сохранить NULL-строку и предлагает удалить override.
Валидация приводит int/float/str/datetime/duration, строго проверяет bool,
структуру choice и неизвестные типы. Ошибки REST возвращаются как HTTP 400, а
не 500. Публичная сигнатура `set_value()` сохранена; при reset она возвращает
`None`. Все 63 теста проходят, Django system check чистый, изменений моделей
после migration `0004` нет.

## 8. Исправить кэширование

Статус: выполнено 2026-07-30 без зависимости от backend-specific
`delete_pattern`.

План:

- при изменении global value очищать пользовательские ключи `is_enabled`,
  вычисленные через global fallback;
- очищать frontend-кэш и при переключении `frontend` с `True` на `False`;
- использовать отдельный sentinel, чтобы отличать отсутствие кэша от
  закэшированного `None`;
- проверить инвалидацию при сохранении и удалении `SettingValue` и
  `SettingDefinition`;
- добавить тесты global fallback, user override, изменения `enabled`, изменения
  `frontend` и удаления данных.

Критерий готовности: после записи или удаления следующий read возвращает
актуальное значение для глобального и пользовательского контекста.

Результат: `is_enabled()` хранит user-key только для реального user override,
а global/default fallback — в общем ключе. Поэтому изменение или удаление
global value сразу видно всем пользователям без перечисления cache keys. При
изменении definition очищаются global и известные user keys; frontend-кэш
очищается после global value и любого изменения definition, включая
`frontend=True → False`. Cache lookup использует sentinel, пустой frontend
response кэшируется, caller default отсутствующего флага не залипает. Все 71
тест проходят, Django system check чистый, новых миграций нет.

## 9. Исправить snapshots

Статус: выполнено 2026-07-30 с безопасным preview/dry-run API.

План:

- при `has_global_value=False` удалять существующее глобальное значение;
- валидировать полный payload до удаления или изменения текущих данных;
- безопасно обрабатывать пустой и повреждённый snapshot;
- определить политику для категорий, которых нет в снимке;
- добавить preview/dry-run на уровне сервиса;
- проверить транзакционность: любая ошибка должна откатывать восстановление;
- добавить тесты удаления global value, повреждённого payload и rollback.

Критерий готовности: после restore состояние определений и глобальных значений
точно соответствует валидному снимку, а ошибка не оставляет частично
восстановленные данные.

Результат: payload полностью валидируется и нормализуется до изменений;
дублирующиеся/некорректные ключи, типы, flags, categories, choices и values
отклоняются. Отсутствующий global value удаляется, legacy NULL трактуется как
отсутствующий override. Пустой snapshot требует `allow_empty=True`. Добавлены
`preview_global_settings_snapshot_restore()` и `dry_run=True`. Restore остаётся
атомарным, категории намеренно не удаляются как потенциально общие данные.
Admin показывает validation error без частичного restore. Все 76 тестов
проходят, Django system check чистый, новых миграций нет.

## 12. Финальная проверка

Статус: выполнено 2026-07-30. Подробный отчёт сохранён в
`docs/2026-07-30-release-verification.md`.

Обязательные команды:

```bash
pytest
python manage.py check
python manage.py makemigrations --check --dry-run
python -m build
```

Матрица проверки установки:

1. Только Django и основной пакет.
2. Django + extra `drf`.
3. Django + extras `drf` и `docs`.
4. Минимальная и максимальная поддерживаемые версии Django.

Итоговые критерии:

- весь тестовый набор проходит;
- Django system check не показывает предупреждений проекта;
- миграции воспроизводимы с нуля и применяются к существующей БД;
- wheel и sdist собираются и устанавливаются;
- README соответствует публичному API и фактическим CLI-командам.

Результат: 82 теста проходят без warnings; Django check чистый; migration
state совпадает с моделями. Wheel и sdist собраны из временной копии, проходят
`twine check` и устанавливаются. Smoke matrix прошла для core-only, актуальных
DRF/docs, Django 3.2.25, Django 6.0.7 и минимальных extras DRF 3.14.0 +
drf-yasg 1.21.5. Python 3.10 отсутствует на машине, поэтому нижняя граница
Python отдельно не запускалась; Django 3.2 проверен на Python 3.11. Версия
установлена в `0.5.0`; финальные артефакты собраны, прошли `twine check` и
опубликованы в PyPI.
